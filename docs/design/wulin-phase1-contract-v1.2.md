## 二、模块与输入契约

| 模块 | 责任 | 交付边界 |
| --- | --- | --- |
| 规则类型 | 战斗、角色、武学实例、主招、状态与事件 | 稳定 ID；整数资源；明确来源与作用范围 |
| 内容目录 | 六门先行书、蓄震、三类标准敌人与引导 | 数值来自现有文档；装配需过容量和技能位校验 |
| 规则引擎 | 准备、轮初恢复、基础行动、拆招、接招、轮末 | 与 DOM、动画、网络和在线模型解耦 |
| 决策输入 | 姿态、优先级、留力、临时变招 | 承诺后不可回写；记录输入而非依赖点击时机 |
| 日志与账本 | 实际资源变化、付费、跳过、父子因果与终止 | 能从结果定位到对应主招、规则和根连锁 |
| 模拟入口 | 固定案例、完整对局、批量场景报告 | 普通模拟没有研究、银两或材料结算 |
| 状态检查点 | 轮末状态副本、规则／内容版本与输入引用 | 只验证引擎恢复一致；不宣称已实现玩家存档 |

战斗输入至少包括：规则版本、内容版本、双方最大与当前资源、兵器 ID、武学实例／来源版本、装备位、优先级、留力、敌人配置、当前段落 ID 与段落内序号、已抽定的下一段落、战斗种子及其消耗位置、已承诺决策。首轮输入内力在自然恢复之前；已有手算中的“已含自然恢复”案例必须直接在其指定阶段构造，不能再加一次。

结束原因至少区分玩家胜利、玩家败退、决策不足、安全上限和非法输入。安全上限与没有提供下一条决策都不算普通获胜或平局。

## 三、必须固定的执行细节

1. **共同准备与冻结。** 轮初先识别待跳过的行动，再提交双方未跳过的架招状态。双方准备都提交后才处理准备连锁。后来新产生的冻结不能撤销已经使用的架招，只能作用于下一次尚未执行的基础机会。
2. **主招的格挡作用域。** 一层护势锁定一门主招；多段按逐击击前架势判断，崩溃之后的后续打击不再格挡。该主招完成才消费护势；不能把整条接招链当成同一主招。
3. **整数伤害。** 威力经明确修饰后乘格挡系数，最终伤害向下取整，再截断到当前气血。例如威力 3 格挡后扣气血 1；架势威力不乘格挡系数。
4. **受击方先响应。** 先完成一门主招的逐击事实，再按受击方同批优先级结清防御响应；原出手者仍在场，才执行自己的变化、收势与跨门接招。新事实生成的下一批不插队已经锁定的候选批。
5. **付费与留力。** 发动前检查现有内力；追加攻击付款后不得低于留力。不能借未来回气；失败不付款、不产生完成或收势。只有新事实能提供新机会，后续回气不重新扫描旧的失败事实。
6. **破绽的归属与期限。** 按制造者下一次新的基础行动实例结束失效；架招与被冻结跳过的机会都计入。崩溃当击不能追溯加伤；不复制、不刷新、不让普通多段无收益地吞掉它。
7. **冻结保护。** 第一次跳过后，保留一个不会再被同类冻结跳过的基础行动机会；保护结束前寒意上限 2。每个角色用单调递增的基础行动 ID 标识机会，保护持续到该受保护行动及其整根连锁结束。状态和待跳过／保护机会单独记录，不能用一个布尔值混为一谈。
8. **根连锁与次数。** 每个角色的一次基础行动建立独立根；共同准备先提交双方架招，再按玩家→敌人结清各自架招根。轮初自然恢复也先同时提交双方数值，再按玩家→敌人分别建立边界根处理事实。反击、追击及派生回气沿用触发根，不为刷新次数另开根。角色＋武学实例＋组件规则构成限次身份。回气内功额外每轮一次，蓄震每根一次。已付款三连的三击不被限次压成一击。
9. **敌人段落。** 每轮锁定意图与允许主动接招的名单；轮末推进一次，即使被冻结、基础未接触或技能缺气。当前段落最后一项锁定时抽取下一段落，恰好消耗一次战斗随机数并立即公开；具名课题与引导配置只循环段落 A，不抽取。被动仍需真实事实、内力和本人存活，不补行动、不暗中换招。
10. **死亡与诊断。** 气血为零立即停止后续攻击、状态与收益；预算触顶停止未执行工作并报告原因，不能伪造正常完成、胜利、回气或奖励。

同类状态已经存在且本次没有合法增量时，在支付前跳过，记“状态已存在”，不扣费、不占成功限次；纯回气在内力已满时同样处理。复合资源技能只有在全部声明效果都无合法增量时才如此跳过。攻击即使随后被闪避仍支付并占限次。失败事实 ID 与成功发动限次分开记录，跳过不会因后来资源变化重扫同一事实。

以上细节作为实现检查口径。若原型发现无法兼容的例子，先登记冲突及修改原因，并同步规则文档；不在代码中偷偷选择另一种结果。

## 四、验收案例与独立预期

| 案例 | 输入重点 | 验收结果 |
| --- | --- | --- |
| 寒霜破势同根 | 沿用战斗规则 §11.1：内力 10，敌气血 30／架势 10，留力 0 | 整根伤血 19，玩家内力 5；敌尚未行动则被冻结跳过 |
| 留力阻止追击 | 同上，仅留力改为 4 | 敌剩气血 17，玩家内力 6，破绽保留；追击不付款、不回气 |
| 受击反震优先 | 三连三次接触，守卫存活且可付 2 | 先反震威力 6，再轮到玩家后续接招；玩家致死则追击取消 |
| 只有两次接触 | 三连的一击被身法闪避 | 蓄震按两次接触反击威力 4，不能按三击或整个根累加 |
| 完全闪避基础出招 | 目标有一份身法，无其他事实 | 本次基础接触起势的技能不发动、不付款 |
| 格挡仍能开招 | 基础出招被格挡但接触 | 接触起势仍合法；其后主招重新按自己的防御状态判断 |
| 同批回气再反击 | 沿用战斗规则 §11.4，资源为已含轮初恢复的窗口输入 | 归息先回 2，借力付款 3；结果与文档账本一致 |
| 破绽跨轮 | 当前根未消费，制造者下一行动才发生 | 轮末仍有效；下一新基础行动及连锁结束后过期 |
| 冻结与架招 | 分别在准备前及架招已提交后冻结 | 前者跳过准备，后者不撤销准备；都不能额外送基础行动 |
| 死亡与限次 | 多段中途致死、反击链、每轮回气上限 | 死亡后停止；同事件不重发；安全终止与胜负分开 |
| 轮末恢复一致 | 保存、复制、继续同一输入序列 | 最终状态与事件顺序一致；预览不改变原状态和正式事件序号 |
| 非法构筑 | 超容量、超过四门、负资源、无效内容 ID | 执行前给出可解释错误，不生成半场奖励或战斗结果 |
| 段落抽取 | 同一种子与输入重放；另以冻结跳过段落最后一项 | 段落序列一致；跳过不顺延；抽取时点与随机数消耗次数不变 |
| 固定段落 | 引导配置与具名课题实例 | 只循环段落 A，不消耗战斗随机数 |

这些是独立手算预期，不以调用被测函数生成“正确答案”。敌人细则里的刀客演算留作其接入阶段验收，不假装第一阶段已经支持所有内容。

## 五、构筑实验与难度比较

### 5.1 三个先行构筑

| 构筑 ID | 武学 | 容量 | 验证的问题 |
| --- | --- | ---: | --- |
| `cold_chain` | 叠寒剑、崩势追击、归息诀 | 12 | 控制与追击是否抵得上内力和反震风险 |
| `guard_counter` | 归息诀、借力诀、踏风步、断势击 | 12 | 主动破势、防反与身法是否有实际用途 |
| `guard_break` | 断势击、崩势追击、归息诀 | 10 | 单击破势与破绽兑现是否形成不同优势 |

比较时都使用铁剑、四武学位上限、容量上限 12，先固定气血 30、架势 20、开场内力 10（上限 20）。没有塞满容量不是违规；也不把空余容量暗换成免费属性。后续兵器实验另列成本，不能只给其中一套额外药品或更强武器。

### 5.2 种子与有效样本

本阶段没有随机命中骰子。种子只决定敌人的段落序列：同一种子与输入必须得到同一结果；不同种子产生不同段落序列，可以作为不同样本。每格使用一组预先固定的 20 个种子（首轮提案），报告胜率时同时列出覆盖到的段落序列；不得事后挑选有利种子。

先使用三构筑 × 三标准敌人 × 三份公开决策策略的 27 格矩阵，第一阶段不带词缀。三策略分别为始终出招、按公开攻防／回气窗口选择姿态、以架招和反击为主并在调息窗口进攻。每份策略都要写明姿态、留力、优先级与决策条件，避免事后为一格偷偷人工选择最优动作。

矩阵用于发现明显无效路线、万能策略和停滞对局，不把三份策略称为最优解。难度判断还需同条件的人工解法：每类标准敌人至少两种当前可达方案，至少一解不依赖它自己的首通奖励。

初步设计目标是三构筑各能在至少两类标准敌人上找到可复现的胜利，并至少有一组对手使构筑优劣排序交换。比较轮数、耗血、净内力和正常结束比例；目标未达到时报告真实结果并调整数据，不更换标签冒充通过。

### 5.3 成长与连续遭遇的后续检查

第一阶段只比较构筑差异，不据此宣称已经实现研究、器物或故事成长。后续用相同敌人配置对照“初始两门 → 成熟套路 → 合法改良”来观察进步；路线结转资源与医药准备单独报告。

旧敌人原强度保持；论艺是单独配置。成熟构筑是否更稳、更省资源、能否应对新配合，要靠后续实际结果确认。

## 六、完成标准与报告

第一阶段只有在以下证据齐备时才标为完成：

- 本作工程可按自己的说明在干净环境执行，核心规则支持离线、无界面的独立验证。
- 规则测试覆盖上述关键边界且通过；状态与事件能对应到规则和独立手算预期。
- 四份先行敌人配置和六门玩家模板、蓄震均通过内容校验。
- 同输入重放、状态副本预览和轮末恢复一致；不发永久奖励。
- 27 格矩阵真实运行并输出原始指标、失败和异常；可玩性目标是否成立单独标注。
- 报告列明仍未支持的内容和待调参数，不将规则正确、难度合适、真人觉得有趣混为一项完成。

命令、测试数、输出文件、内容版本和提交 ID 由真实运行结果补入，不提前填成功结论。第一阶段过关后再接 Phase 2 的界面、逐轮选择、改良与版本对比。
