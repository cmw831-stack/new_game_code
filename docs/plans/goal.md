# 持续开发目标（Goal）V2：更深，而不是更大

**日期：2026-10-29**（V1 写于 2026-10-28，按功能清单推进 M2–M4；本版改为按证据推进）

**用途：** 给每个开发会话一个固定的方向和工作循环。新会话先读 [CLAUDE.md](../../CLAUDE.md)、[PROGRESS.md](../../PROGRESS.md)，再读本文件。本文件只定目标和做法，不是规则；规则以 `docs/design/` 最新版本为准，进度以 PROGRESS.md 为准。

## 一、最终目标与阶段

交付策划书第十三章的完整新版 MVP（Phase 6）。每个阶段只回答一个问题，答清楚再进入下一阶段（主计划 V1.9.1 13.3 节）：

| 阶段 | 要回答的问题 | 状态 |
| --- | --- | --- |
| Phase 1 规则引擎 | 规则能无界面运行，关键算例可手算复现 | 完成 |
| **Phase 2 构筑实验室** | 玩家输掉一场后，愿不愿意、能不能改一处武学再打赢 | **功能已做完；证据未齐** |
| Phase 3–6 | 生活闭环、完整自创、采矿锻造、整合 | 未开始 |

## 二、Phase 2 的三个可证伪命题

Phase 2 的功能已经够用。剩下的工作不是再做功能，而是证明（或推翻）下面三件事。每件事都写明证据、通过标准和推翻后怎么办。

| 编号 | 命题 | 证据从哪来 | 推翻后 |
| --- | --- | --- | --- |
| **H1 规则正确** | 引擎算出的每一轮结果，都等于策划规则的结果 | 独立参考实现对拍、不变式、变异测试、文档手算 | 先修引擎；所有基于引擎的报告标“需重跑” |
| **H2 系统上有路** | 在最优打法下：没有一套构筑或一种打法通吃三类敌人；大多数“输”的局面存在一处改动可以翻盘；三种姿态各有不可替代的时机 | 求解器对全部合法构筑的穷举 | 数值或规则出了结构问题，交负责人决定改什么，不靠真人试玩去掩盖 |
| **H3 人会走这条路** | 真人在没有提示时，输了会改一处再打，并能说出原因 | 外部试玩者的行为、原话与导出记录 | 先改教学和界面；仍不成立则回到 H2 检查“改一处”是否太难发现 |

## 三、范围冻结

- Phase 2 **不再加新功能**。只做三类事：为证据服务的工具、修错、修试玩中发现的卡点。
- 新想法写进 PROGRESS.md 的“待办池”，Phase 2 评估结束后再排。
- 待决的 Q13–Q16 中，只处理让试玩能开始所必需的（Q13 发布、Q14 第十课、Q15 开放方式）；Q16 词缀调参并入 E2，用求解器的结果决定。

## 四、证据工作（按顺序做）

### E0 让外部检查真正生效

- 现在的自动检查只在 `main` 和 PR 上运行，开发分支上的提交从未经过它。先让开发分支每次推送也在干净环境运行 `npm run check`。
- 检查结果以 GitHub 上的运行记录为准，不以本地输出为准。

### E1 规则正确（H1）

1. **独立参考实现**：由一个只读策划文档、看不到 `src/` 的独立代理，按战斗细则 V1.2、组件细则 V1.2、敌人细则 V1.3 写一份最小结算实现（可用另一种语言），覆盖三姿态、三资源、护势、破绽、寒意与冻结、留力、限次、蓄震。写不出来的地方就是文档不清楚，记进冲突报告。
2. **对拍**：用属性测试（fast-check）随机生成构筑、资源、敌人意图和决策序列，两边逐轮比较。不一致时回到文档裁决，裁决写进实现说明第四节；不许为了对上而改参考实现。
3. **不变式**（每次随机运行都检查）：内力账本守恒；预览等于实际结算；同输入重放一致；资源不越上下限；事件序号单调；每根连锁的事件数不超过安全上限。
4. **变异测试**（Stryker）：先测规则核心的变异分数作为基线，再把存活的变异逐个补测试或说明为何等价。
5. **文档手算**：保持现有做法，只从文档推导预期。

### E2 系统上有路（H2）

敌人行为公开且确定（种子只决定段落顺序），所以每一局是单人规划问题，可以精确求解。

1. **求解器**：对给定构筑、敌人、种子，用带记忆的搜索求最优姿态与变招序列（状态哈希、剪枝、轮数上限）。先在小局面上用穷举验证求解器本身。
2. **全构筑穷举**：先行六门里所有合法构筑（四个武学位以内、容量 12 以内、含优先级顺序与留力档位）× 三类标准敌人 × 固定 20 个种子 × 无词缀与六个词缀。
3. **指标**（运行前写定，见第五节）：
   - 每套构筑对每个敌人的最优胜负与余量（剩余气血、轮数）；
   - **被支配的构筑**（在所有敌人上都不比另一套好）与**万能解**；
   - “一直出招”和其他固定打法与最优打法的差距；
   - **关键轮比例**：选错就会从赢变输的轮数占比（衡量选择是否有意义）；
   - **改一处翻盘率**：最优打法下输掉的构筑中，存在单处改动（换一门、单槽改良、调优先级或留力）能转为胜利的比例；
   - 每种姿态成为唯一最优选择的局面占比。
4. 用这些指标重新检查 Q11（破势路线）、Q16（词缀）和 V1.9.1 的敌人数值。原来的四种写死打法保留，作为“普通玩家”参照，不再作为主要证据。

### E3 人会走这条路（H3）

1. **负责人先玩一次**：用无痕窗口按[试玩包](phase2-playtest-kit.md)走一遍，不看文档，记下卡点。
2. **外部试玩**：约 5 位不参与开发的玩家，出声思考，按观察表记录，结束时导出记录。
3. **快速迭代**：每 1–2 人后只修“明显卡住”的问题再继续，每次修改写清楚改了什么、为什么。
4. **对照**：把真人的选择与 E2 的最优选择逐轮比较——在哪些轮次偏离最优、偏离后是否因此输掉、输后是否改了一处。

## 五、判定标准

以下门槛是**首轮提案，需负责人确认后生效**；运行前写定，看到结果后修改必须经负责人同意并在报告里如实记录。

| 命题 | 通过标准（首轮提案） |
| --- | --- |
| H1 | 对拍 10 万组随机输入零差异（或差异全部已由文档裁决）；不变式零违反；变异分数达到基线后不下降 |
| H2 | 没有构筑在三类标准敌人上都最优必胜且余量最高；“一直出招”在至少两类非教学敌人上不是最优；改一处翻盘率 ≥ 50%；三种姿态都各自是至少 10% 局面的唯一最优选择 |
| H3 | 5 人中至少 3 人在第一次失败后改一处再战，并能说出改动的理由；没有人因为界面卡住超过 2 分钟而需要提示 |

## 六、证据等级

报告和 PROGRESS.md 里的每条结论都标注依据：**[手算]** 文档推导、**[对拍]** 两份独立实现一致、**[求解]** 最优打法穷举、**[模拟]** 写死打法批量运行、**[真人]** 试玩观察。

- 没有 [对拍] 的引擎结论，不写进策划书。
- 没有 [真人] 的体验结论，只写“待验证”。
- [模拟] 不能单独支撑数值调整。

## 七、除了 Claude 和负责人，谁来证明

- **干净环境的自动检查**（GitHub Actions）：证明测试不是只在本机通过。
- **独立参考实现**：证明引擎和文档一致，而不是和 Claude 自己的理解一致。
- **随机属性测试与变异测试**：证明测试真的能抓到错误。
- **求解器的穷举结果**：证明结论覆盖了全部构筑和最优打法，不是挑出来的样本。
- **外部试玩者**：证明真人会这样玩，而不是设计者以为会这样玩。
- **可复现的脚本、固定种子和导出记录**：任何人都能重跑得到同样的数字。

## 八、每个会话的工作循环

1. **对齐**：读 CLAUDE.md、PROGRESS.md、本文件；`npm run check` 确认基线；看 GitHub 上最近一次检查是否通过。
2. **选任务**：取第四节中第一个未完成、未阻塞的证据任务。先写下它服务于 H1、H2、H3 中的哪一个；**哪个都不服务的，不是 Phase 2 的工作**。
3. **先定标准**：涉及模拟、求解或试玩的，先把判定标准写进报告开头再运行。
4. **实现与验证**：测试预期只来自文档或独立实现；`npm run check` 通过；改网页时在浏览器走一遍。
5. **记录**：结论标证据等级；PROGRESS.md 更新命题状态（未检验／通过／推翻／部分成立）。
6. **提交与汇报**：中文提交；汇报只说本轮让哪个命题前进了多少、证据是什么、下一步。

## 九、必须停下来问负责人的情形

- 任何一个命题被推翻，或判定标准需要修改。
- 需要新增或修改策划书数值，或新建策划书版本。
- 推送到 `main`、更新试玩链接、对外分享、联系试玩者。
- 范围增减（包括想加任何新功能）。
- 连续两次尝试仍无法让测试按文档预期通过。

## 十、持续推进模式

负责人说“持续推进”时适用，直到负责人说“停”：

- 每完成一步，提交并推送到本会话的开发分支；不推送 `main`，不合并。
- 需要拍板的问题写进 PROGRESS.md“待决问题”并附推荐，转做下一个不受影响的证据任务；全部被阻塞时暂停汇报。
- 每轮汇报几行：推进了哪个命题、证据等级、提交号、新增待决问题。

## 十一、可直接使用的目标提示

> 按 `docs/plans/goal.md`（V2）推进《武林·自创绝学》Phase 2：不再加功能，只为三个命题收集证据——H1 引擎等于策划规则、H2 最优打法下系统有路（无万能解、改一处能翻盘、三种姿态各有用处）、H3 真人输了会改一处再打。先读 CLAUDE.md、PROGRESS.md、goal.md，`npm run check` 确认基线；取第四节第一个未完成的证据任务，先写明它服务哪个命题、判定标准是什么，再实现、验证、记录证据等级（手算／对拍／求解／模拟／真人），中文提交并推送到本会话的开发分支。命题被推翻、标准要改、要加功能或要对外发布时停下来问负责人；全部任务被阻塞时暂停汇报。
